### 🧮 DESAIN AST UNTUK FORMULA (Tanpa `eval`)

Untuk rumus TKDN dan preferensi harga, saya mengusulkan struktur AST terbatas yang akan divalidasi ketat oleh backend (menggunakan Zod schema di Drizzle/Node.js).

**Contoh AST untuk Rumus Preferensi Harga:**
`Harga Evaluasi = Harga Penawaran * (1 - (Persentase Preferensi / 100))`

```json
{
  "type": "operator",
  "operator": "multiply",
  "operands": [
    { "type": "reference", "path": "offered_price" },
    {
      "type": "operator",
      "operator": "subtract",
      "operands": [
        { "type": "literal", "value": 1 },
        {
          "type": "operator",
          "operator": "divide",
          "operands": [
            { "type": "reference", "path": "preference_percentage" },
            { "type": "literal", "value": 100 }
          ]
        }
      ]
    }
  ]
}
```

**Validator Zod untuk AST (Contoh Implementasi Backend):**
```typescript
import { z } from 'zod';

// Definisi node AST yang diizinkan
const LiteralNode = z.object({
  type: z.literal('literal'),
  value: z.union([z.number(), z.string(), z.boolean()])
});

const ReferenceNode = z.object({
  type: z.literal('reference'),
  path: z.string().regex(/^[a-zA-Z0-9_.]+$/) // Hanya alfanumerik dan underscore, mencegah injeksi
});

const OperatorNode: z.ZodType<any> = z.lazy(() => 
  z.object({
    type: z.literal('operator'),
    operator: z.enum(['add', 'subtract', 'multiply', 'divide', 'min', 'max', 'if_then_else']),
    operands: z.array(z.union([LiteralNode, ReferenceNode, OperatorNode]))
  })
);

export const FormulaAstSchema = z.union([LiteralNode, ReferenceNode, OperatorNode]);
```

**Evaluator Aman di Backend:**
```typescript
function evaluateAst(ast: any, context: Record<string, any>): number {
  if (ast.type === 'literal') return ast.value;
  if (ast.type === 'reference') {
    const val = context[ast.path];
    if (typeof val !== 'number') throw new Error(`Reference ${ast.path} is not a number`);
    return val;
  }
  if (ast.type === 'operator') {
    const operands = ast.operands.map((op: any) => evaluateAst(op, context));
    switch (ast.operator) {
      case 'add': return operands[0] + operands[1];
      case 'subtract': return operands[0] - operands[1];
      case 'multiply': return operands[0] * operands[1];
      case 'divide': 
        if (operands[1] === 0) throw new Error('Division by zero');
        return operands[0] / operands[1];
      // ... operator lain
      default: throw new Error('Unknown operator');
    }
  }
  throw new Error('Invalid AST node');
}
```

### 🗺️ ROADMAP IMPLEMENTASI (Sesuai Arahan Anda)

Saya setuju sepenuhnya dengan urutan yang Anda berikan. Berikut adalah rencana eksekusi untuk **Fase 1 (Fondasi Database)**:

**Langkah 1: Hierarki Sumber Hukum & Pasal**
*   Membuat tabel `legal_sources` dan `provisions`.
*   Menyiapkan mekanisme *soft-delete* dan *timestamp*.

**Langkah 2: Aturan, Kondisi, dan Override**
*   Membuat tabel `business_rules`, `rule_conditions`, `rule_overrides`.
*   Mengimplementasikan validator AST untuk `formula_ast`.

**Langkah 3: Policy Pack dengan Versi & Snapshot**
*   Membuat tabel `policy_packs` dan `policy_pack_rules`.
*   Merancang logika *snapshotting*: Saat status pack berubah dari `REVIEWED` ke `PUBLISHED`, sistem secara otomatis menyalin `default_value` dan `formula_ast` dari `business_rules` ke kolom `snapshot_value` dan `snapshot_formula_ast` di `policy_pack_rules`.

**Langkah 4: Snapshot Keputusan & Audit Log**
*   Membuat tabel `decision_references` dan `audit_logs`.
*   Mengimplementasikan *database trigger* atau *Drizzle middleware* untuk memastikan `audit_logs` hanya bisa `INSERT`.

**Langkah 5: Seed Awal (Perpres 46/2025 & Permenperin 35/2025)**

*   **PENTING:** Semua entri akan memiliki `verification_status = 'UNVERIFIED'` secara *default*. Tim hukum harus meninjau dan mengubahnya menjadi `VERIFIED` setelah mencocokkan dengan naskah resmi.

**Langkah 6: API Evaluasi Aturan & Antarmuka Admin**
